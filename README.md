## Course Reflections

### 1. Interpreting User Needs into Software Requirements
Translating high-level user needs into functional software requires breaking down ambiguous client requests into explicit, testable criteria. Writing user stories bridges this gap by framing features from the user's perspective (`As a... I want... So that...`). Defining clear acceptance criteria and a strict Definition of Done during story creation prevents scope creep and ensures development and testing efforts directly deliver measurable business value.

### 2. Approach to Software Development & Future Agile Practices
My approach to program development centers on modularity, iterative progression, and continuous feedback. Rather than attempting to build entire systems upfront, breaking functionality into manageable increments allows for rapid adaptation when project parameters shift mid-development (such as adjusting GUI layouts and data models). Moving forward into future software engineering work, I will prioritize short feedback cadences, early and continuous integration testing, and maintaining clear visual transparency across technical dependencies.

### 3. What It Means to Be a Good Team Member
Being an effective team member in software development means combining technical precision with proactive, unambiguous communication. It involves taking shared ownership of code quality, actively identifying and communicating blockers before they become critical bottlenecks, and being adaptable when requirements evolve. A strong team member provides clear, actionable feedback to peers—such as explicit parameter callouts during bug fixes—to minimize friction and keep the entire team moving toward a shared goal.
